# Phase 1: Frequently Asked Questions (FAQ)

---

### Q1: Why did you replicate classical baselines instead of relying on published numbers from Danyliuk (2026)?
**Answer:** In systems research, raw performance numbers depend heavily on processor clock frequency, micro-architecture, cache hierarchy, memory bus speed, and Linux kernel versions. Comparing our Phase 2 shared-memory engine measured on local hardware against Danyliuk's numbers measured on an older 3.3 GHz testbed would be methodologically invalid. Replicating the baselines locally provides an identical experimental control.

### Q2: Why did you use `CLOCK_MONOTONIC_RAW` instead of `CLOCK_REALTIME` or `rdtsc`?
**Answer:** `CLOCK_REALTIME` is subject to NTP clock adjustments, frequency slewing, and leap seconds, which can introduce negative elapsed time or sudden jitter. Direct `rdtsc` instructions are processor-frequency dependent and can be skewed if a process migrates across CPU sockets with unsynchronized TSCs. `CLOCK_MONOTONIC_RAW` provides linear, nanosecond-precision hardware ticks unaffected by NTP slewing.

### Q3: Why is CPU core affinity pinning necessary?
**Answer:** Without pinning via `sched_setaffinity()`, the Linux Completely Fair Scheduler (CFS) frequently migrates producer and consumer threads across CPU cores to balance system load. This migration evicts hot L1/L2 caches, triggers inter-processor interrupts (IPIs), and introduces massive artificial latency spikes in the tail distribution (P99/P99.9). Pinning isolates the communication overhead from scheduler migration noise.

### Q4: Why do Anonymous Pipes and UNIX Domain Sockets exhibit nearly identical latencies (~1.4 μs)?
**Answer:** Both mechanisms rely on kernel-mediated circular memory buffers and require the calling process to enter kernel space via system calls (`write`/`read` or `send`/`recv`). In both cases, the kernel copies data from user space to kernel space, locks the buffer, wakes up the waiting reader thread, and performs a voluntary context switch. The fundamental execution overhead is dominated by the user/kernel privilege boundary transition.

### Q5: Why are POSIX Message Queues slower than Pipes and Sockets?
**Answer:** POSIX message queues provide message prioritization and discrete message boundaries. Internally, the Linux kernel manages POSIX message queues using an augmented red-black tree to order messages by priority. Every `mq_send` involves tree traversal and node insertion, introducing algorithmic CPU overhead compared to simple circular byte stream pointers.

### Q6: Why did Naive Shared Memory with Futex perform poorly (~1.45 μs) on 64-byte payloads?
**Answer:** Naive shared memory suffered from two critical micro-architectural design flaws:
1. **False Sharing:** The synchronization flag and data buffer were placed adjacent to each other in unaligned memory, sharing the same 64-byte hardware cache line.
2. **Immediate Futex Invocations:** Without a bounded micro-spin loop, any slight consumer delay caused the receiver to invoke `SYS_futex`, entering the kernel and triggering an expensive voluntary context switch.

### Q7: What does "2 syscalls per operation" mean in the benchmark results?
**Answer:** For a unidirectional transfer in a blocking IPC channel, the producer must invoke `write()` (1 system call) to enqueue data, and the consumer must invoke `read()` (1 system call) to dequeue data. Thus, exactly 2 system calls are required to transfer a single message through the kernel.

### Q8: What impact do Spectre and Meltdown mitigations have on classical IPC?
**Answer:** As detailed by Danyliuk (2026), Kernel Page-Table Isolation (KPTI) and retpoline mitigations increased the cost of user/kernel privilege transitions from ~45–90 ns to ~100–230 ns per syscall. For a 2-syscall IPC exchange, this imposes an unavoidable tax of ~200–400 ns per message purely for security entry/exit overhead.

### Q9: How did you verify that zero data corruption occurred during benchmark sweeps?
**Answer:** Every message payload was filled with a deterministic byte pattern generated by `aipc_generate_payload()`, which embeds the message sequence counter and payload hash. The receiver executed `aipc_validate_payload()` to verify every byte before recording latency. Across 4,000,000 baseline exchanges, zero errors occurred.

### Q10: Examiner Challenge: "Isn't a round-trip ping-pong test artificial compared to one-way streaming?"
**Answer:** An isolated ping-pong echo test is the industry standard (established by Immich et al., 2003, and used in `ipc-bench`) because it strictly isolates the communication transport overhead from application queuing and batching effects. In pure streaming, measurements reflect buffer absorption capacity rather than pure communication latency. Both metrics are valuable: Phase 1 evaluates pure latency, while Phase 4 evaluates streaming throughput.
